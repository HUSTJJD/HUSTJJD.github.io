Computer Organization

Base Knowledge, Computer Organization 2025-08-10 2026-10-10 4376 字

自动关联目录：Computer Organization

组成原理回答的是：指令是怎么被执行的，以及为什么有的代码快有的代码慢。

它位于软件与硬件的边界。理解它，才能解释很多"看起来莫名其妙"的性能现象：

  • 为什么按行遍历比按列遍历快几十倍
  • 为什么分支预测失败那么贵
  • 为什么 ++i 和 i++ 在有些场景有区别
  • 为什么多线程不一定更快（伪共享）

冯·诺依曼结构

┌──────────┐
│   CPU    │  ← 控制器 + 运算器 + 寄存器
└────┬─────┘
     │ 总线
┌────┴─────────────────────┐
│  存储器（内存）           │  指令和数据放一起
└──────────────────────────┘

核心特征：存储程序——指令和数据都存在同一个内存里，可以被同样地读写。

冯·诺依曼瓶颈：CPU 和内存之间的带宽是有限的，而 CPU 速度远快于内存 → CPU 经常在等数据。

这就是整个存储层次结构存在的理由。

指令执行

取指-译码-执行循环

1. 取指（Fetch）:     PC → 内存，取指令
2. 译码（Decode）:    解析操作码和操作数
3. 执行（Execute）:   运算
4. 访存（Memory）:    读写内存（如需）
5. 写回（Writeback）: 结果写回寄存器
6. PC += 指令长度

一条指令要 5 步，但流水线让多条指令的不同阶段重叠：

周期:  1   2   3   4   5   6   7
指令1: F   D   E   M   W
指令2:     F   D   E   M   W
指令3:         F   D   E   M   W
       ↑ 5 个周期后，每个周期完成一条指令（吞吐 5 倍）

流水线的三种冒险（Hazard）

类型原因解法
结构冒险硬件资源冲突（两条指令同时要访存）多端口存储器、分离指令/数据缓存
数据冒险后一条指令需要前一条的结果转发（forwarding）、插入气泡（stall）
控制冒险分支跳转，不知道下一条取哪分支预测、延迟槽

数据冒险的例子：

add r1, r2, r3     ; r1 = r2 + r3
sub r4, r1, r5     ; 需要 r1，但 r1 还没写回

转发（bypassing）：不等写回，直接把 ALU 的输出接到下一条指令的输入。

Load-use 冒险无法完全转发（数据从内存来，太晚）：

lw  r1, [r2]       ; 从内存加载
add r3, r1, r4     ; 必须等一个周期（stall）

这就是编译器要做指令调度的原因——在 lw 和 add 之间塞入无关指令。

分支预测

分支错误预测的代价 = 清空流水线 ≈ 15~20 个周期。

预测器演进：

类型思路
静态永远预测不跳转 / 向后跳预测跳转（循环）
2-bit 饱和计数器记录每个分支的历史，连续错两次才改变预测
局部历史（BHT）每个分支自己的历史模式
全局历史（GShare）用全局的分支历史索引
TAGE / 感知机现代高性能预测器，多个历史长度的表 + 投票

准确率：现代预测器 > 95%。

对程序员的意义：

// 慢：随机分支，预测失败率 ~50%
for (int i = 0; i < n; i++)
    if (data[i] < 128) sum += data[i];      // data 随机

// 快：排序后前一半都小于 128，预测器几乎全对
std::sort(data, data + n);
for (int i = 0; i < n; i++)
    if (data[i] < 128) sum += data[i];

这个著名的例子：排序后的数组遍历比未排序快 2~3 倍，纯粹因为分支预测。

无分支写法（编译器 -O2 有时会自己做）：

sum += (data[i] < 128) ? data[i] : 0;     // 可能被编译成 cmov
// 或
sum += data[i] * (data[i] < 128);         // 算术消除分支

存储层次

为什么需要层次

CPU 寄存器:  ~0.3 ns    几百字节
L1 Cache:    ~1 ns      32~64 KB
L2 Cache:    ~4 ns      256 KB ~ 1 MB
L3 Cache:    ~10 ns     8~64 MB（多核共享）
主内存:      ~80 ns     8~64 GB
SSD:         ~100 μs    ← 慢 1000 倍
机械硬盘:    ~10 ms     ← 慢 10 万倍
网络:        ~10~100 ms

速度差 3 个数量级，成本差也是——所以只能分级。

局部性原理（层次结构有效的前提）：

  • 时间局部性：刚访问过的数据很快会再访问
  • 空间局部性：访问了一个地址，附近地址很快会访问

Cache 的结构

地址: [Tag | Index | Offset]

      ┌──────────────────────┐
      │  Set 0: [way0][way1]...│   每个 way 是一行（cache line）
      │  Set 1: [way0][way1]...│
      │  ...                   │
      └──────────────────────┘

Cache line（缓存行）：内存和 cache 之间传输的最小单位，64 字节（x86）。

这是性能的关键：读一个 int 实际上会把周围 64 字节都加载进来 → 顺序访问极快。

三种 Miss（3C 模型）

类型原因解法
Compulsory（强制）第一次访问必然 miss预取
Capacity（容量）工作集超过 cache 容量减小工作集
Conflict（冲突）多个地址映射到同一个 set提高相联度、改变布局

替换策略

策略特点
LRU最久未用。理论好，硬件实现贵（需要计数器）
PLRU（伪 LRU）用二叉树的位近似，硬件便宜
随机最简单，实际效果接近 LRU
RRIP现代 Intel 用，考虑"再引用距离"

写策略

策略做法
Write-through同时写 cache 和内存。简单但慢
Write-back只写 cache，淘汰时才写回。快，但有一致性问题

现代 CPU 都用 write-back + MESI 协议保证多核一致。

对程序员的意义

// 慢：按列遍历，每次跳 1 行（跨 cache line）
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];

// 快：按行遍历，顺序访问
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += a[i][j];

N=4096N = 4096N=4096 时差距可达 20 倍以上。

其他优化：

技巧说明
分块（tiling / loop blocking）把大矩阵切成 cache 能装下的小块
数组合并（AoS → SoA）结构体数组 → 数组结构体，只加载需要的字段
对齐让数据对齐到 cache line
避免伪共享不同线程的数据不要在同一 cache line
预取__builtin_prefetch 或硬件自动预取

伪共享（False Sharing）

// 坏：两个线程写相邻的变量，在同一 cache line → 反复失效
struct { int a; int b; } shared;      // 线程1 写 a，线程2 写 b

// 好：padding 到不同 cache line
struct { alignas(64) int a; alignas(64) int b; } shared;

症状：多线程反而比单线程慢。这是最难查的性能问题之一。

指令级并行（ILP）

超标量

一个周期发射多条指令（现代 CPU 4~6 发射）。

乱序执行（Out-of-Order）

指令的实际执行顺序可以不同于程序顺序，只要数据依赖允许。

1. 发射（In-order）:   指令进入 reorder buffer
2. 执行（Out-of-order）: 操作数就绪就执行
3. 提交（In-order）:   按程序顺序写回，保证精确异常

关键：看起来是顺序执行的（对程序员可见的状态），实际是乱序的（内部优化）。

寄存器重命名

消除假依赖（WAR、WAW）：

原始:  add r1, r2, r3     写 r1
       sub r1, r4, r5     又写 r1（WAW 依赖，但其实无关）

重命名: add p1, p2, p3
       sub p4, p4, p5     ← 用不同的物理寄存器，可以并行

x86 只有 16 个架构寄存器，但物理寄存器有 100+ 个。

SIMD

一条指令处理多个数据：

指令集宽度
SSE128 bit（4× float）
AVX / AVX2256 bit（8× float）
AVX-512512 bit（16× float）
NEON（ARM）128 bit
// 编译器自动向量化（需要 -O3 且循环结构简单）
for (int i = 0; i < n; i++) c[i] = a[i] + b[i];

// 手动
#include <immintrin.h>
__m256 va = _mm256_load_ps(&a[i]);
__m256 vb = _mm256_load_ps(&b[i]);
__m256 vc = _mm256_add_ps(va, vb);
_mm256_store_ps(&c[i], vc);

自动向量化的障碍：

  • 循环次数未知（可用 #pragma omp simd 或 -fno-tree-vectorize 检查）
  • 数据依赖（如累加 sum += a[i]，可用 -ffast-math 允许重排）
  • 非连续访问（gather/scatter）
  • 别名问题（restrict 关键字）

多核与缓存一致性

MESI 协议

每个 cache line 有 4 个状态：

状态含义
M（Modified）已修改，与内存不一致，本核独占
E（Exclusive）未修改，与内存一致，本核独占
S（Shared）未修改，多个核共享
I（Invalid）无效

状态转换靠总线嗅探（snooping）：一个核写，其他核的副本失效。

这是多核性能的隐藏成本：看似独立的数据，只要在同一 cache line，就会反复失效。

内存模型

编译器和 CPU 都会重排指令（为了性能），所以：

// 线程1              // 线程2
x = 1;                while (y == 0) ;
y = 1;                print(x);        // 可能打印 0！

内存序：

序保证
Sequential Consistency完全按程序顺序（最严格，最慢）
Acquire / Release单向屏障
Relaxed只保证原子性，不保证顺序

x86 是 TSO（Total Store Order）：store-store 不重排，但 store-load 可能重排（store buffer 导致）。 ARM 更宽松：几乎都可以重排。

C++ 的 std::atomic 让你指定内存序：

std::atomic<int> flag{0};
flag.store(1, std::memory_order_release);      // 前面的写不能移到这之后
int v = flag.load(std::memory_order_acquire);  // 后面的读不能移到这之前

默认 seq_cst 最安全但最慢。理解后再优化。

数字表示

整数

补码（Two's complement）：

-1 的 8 位表示: 1111 1111
取反加一:       ~1 + 1 = 1111 1110 + 1 = 1111 1111  ✓

为什么用补码：加减法可以用同一套电路（不需要区分正负），且只有一个 0。

溢出的坑：

unsigned char a = 200, b = 100;
unsigned char c = a + b;     // 44（整型提升后截断）

// 有符号溢出是 UB
int x = INT_MAX; x++;         // UB！编译器可以做任何事

整型提升：char/short 参与运算时会先提升为 int，这是很多隐式 bug 的来源。

浮点（IEEE 754）

单精度 float (32 bit): [符号1][指数8][尾数23]
双精度 double (64 bit): [符号1][指数11][尾数52]

值 = (-1)^s × 1.mantissa × 2^(exponent - bias)
bias: float 127, double 1023

特殊值：

值表示
±0指数和尾数全 0（符号位可不同）
±∞指数全 1，尾数全 0
NaN指数全 1，尾数非 0

精度问题：

0.1 + 0.2 == 0.3        // false！实际是 0.30000000000000004
                        // 因为 0.1 无法用二进制精确表示

// 正确比较
fabs(a - b) < 1e-9;

累加误差：大量小浮点数相加时误差累积 → 用 Kahan 求和或更高精度。

NaN 的传播：任何涉及 NaN 的比较都是 false（包括 NaN == NaN）。

性能分析

perf stat ./program        # 总览：cycles, instructions, cache-misses, branch-misses
perf record ./program      # 采样
perf report                # 查看热点
perf annotate              # 指令级

# 关键指标
# IPC (instructions per cycle): 现代 CPU 理想 4+，低于 1 说明在等内存
# cache-miss rate: > 5% 就该优化内存访问
# branch-miss rate: > 5% 就该优化分支

Top-down 分析方法：

1. 是不是被内存带宽限制？（cache miss 高）
2. 是不是被分支限制？（branch miss 高）
3. 是不是被依赖链限制？（IPC 低但不 miss）
4. 是不是指令数太多？（没向量化）

常见坑

  • 把"指令少"等同于"快"：现代 CPU 上，cache miss 的代价远超几条指令
  • 以为 i++ 比 ++i 慢：对 int 完全一样（编译器会优化）；对迭代器有理论差异
  • volatile 当成原子操作：volatile 只防止编译器优化，不保证原子性、不保证内存序
  • 伪共享：多线程反而变慢，最难查
  • 对齐问题：未对齐访问在某些架构上会崩或极慢
  • 浮点比较用 ==
  • 有符号溢出：UB，编译器可能做出奇怪的优化（如删掉 if (x + 1 > x)）
  • memcpy 的别名：源和目标重叠时 UB（用 memmove）
  • 忽略分支预测：随机分支是最容易被忽视的性能杀手
  • 以为多核一定快：同步和缓存一致性的开销可能超过收益
