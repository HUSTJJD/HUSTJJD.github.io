CUDA 18 · 综合用例、能力速查与术语表

Programing, Cuda 2026-10-11 2026-10-12 6955 字
# CUDA# Case Study# Reference

从“会写 Kernel”到“能交付系统”

一个完整 CUDA 项目不是单个快 kernel，而是一条可证明的链：

需求与误差预算
      ↓
CPU/高精度 reference + 数据集
      ↓
算法分解与数据布局
      ↓
库 / SIMT / Tile / 多 GPU 选型
      ↓
正确性测试 + Sanitizer
      ↓
端到端 benchmark + profiler
      ↓
瓶颈驱动的优化
      ↓
能力查询、fallback、部署矩阵与回归监控

下面四个用例覆盖规则 stencil、随机模拟、稀疏图和大模型推理，展示如何把前 17 章的知识连起来。

用例一：实时图像处理流水线

目标：批量 RGB 图像经过灰度化、Gaussian blur、Sobel 和 threshold，输出边缘图。要求吞吐稳定，支持任意宽高与 batch。

数据流

CPU decode
   │ pinned ring buffers
   ▼
H2D ─→ RGB→Gray ─→ Gaussian X/Y ─→ Sobel+threshold ─→ D2H/encoder
      stream 0 image k
H2D ─→ RGB→Gray ─→ Gaussian X/Y ─→ Sobel+threshold ─→ D2H/encoder
      stream 1 image k+1

先用 NPP/nvJPEG 等库建立基线。若格式或融合需求不匹配，再写自定义 kernel。

映射与布局

  • block 用二维 shape，例如 32×8 或 16×16；
  • 行主序图像让相邻 threadIdx.x 访问相邻像素；
  • pitch/stride 是字节数，不可假定 width*sizeof(pixel)；
  • blur/stencil 用 shared tile 加 halo；
  • border mode 明确为 clamp、reflect、wrap 或 zero；
  • RGB packed 与 planar 布局要分别 benchmark。
shared tile for radius=1

  halo halo halo halo halo halo
  halo  x    x    x    x  halo
  halo  x  output output x  halo
  halo  x  output output x  halo
  halo  x    x    x    x  halo
  halo halo halo halo halo halo

Kernel 骨架

template<int BX, int BY>
__global__ void sobel(const std::uint8_t* in, std::size_t in_pitch,
                      std::uint8_t* out, std::size_t out_pitch,
                      int width, int height) {
    __shared__ std::uint8_t tile[BY + 2][BX + 2];
    int x = blockIdx.x * BX + threadIdx.x;
    int y = blockIdx.y * BY + threadIdx.y;

    // 协作加载中心和 halo；所有线程必须到达 barrier。
    load_clamped_tile(tile, in, in_pitch, x, y, width, height);
    __syncthreads();

    if (x < width && y < height) {
        int gx = gradient_x(tile, threadIdx.x + 1, threadIdx.y + 1);
        int gy = gradient_y(tile, threadIdx.x + 1, threadIdx.y + 1);
        row_ptr(out, out_pitch, y)[x] = saturate(abs(gx) + abs(gy));
    }
}

重点不是复制辅助函数，而是 barrier 必须位于边界 if 外；否则边缘 block 的一部分线程提前退出会导致未定义行为。

优化次序

  1. 先把 decode/transfer/kernel/encode 分段计时；
  2. pinned buffers + 多 stream 重叠多张图；
  3. 消除 RGB→Gray 与 blur 间的中间 round trip；
  4. shared halo 降低重复 global load；
  5. 批量稳定后用 CUDA Graph 降低 launch overhead；
  6. 只有 profiler 显示算术热点，再考虑 vectorized load 或 fast math。

测试矩阵

类别样例
尺寸0×0、1×1、小于 block、奇数、4K
stride紧密、额外 padding、非默认 pitch
内容全黑、全白、单像素脉冲、棋盘、随机
边界四角、最后一行/列、radius 大于尺寸
批次1、2、并发 stream 数以上

用例二：Monte Carlo 期权定价

目标：模拟几何布朗运动终值，计算 discounted payoff 的均值和置信区间。

数据流与算法

sample id
   ↓ counter/subsequence RNG
normal Z
   ↓ path/payoff（可与 RNG 融合）
payoff
   ├─ sum(payoff)
   └─ sum(payoff²)
          ↓
mean + variance + confidence interval

大数组不是必需：每个线程可生成多个样本并做局部累加，再用 CUB reduction 合并 {sum, sumsq}。这样减少显存流量。

数值与统计正确性

  • 累加采用 double 或经过验证的分层 float；
  • variance = E[x²]-E[x]² 在方差很小时可能发生消减，必要时用更稳定算法；
  • 固定 seed 只保证可复现实验，不证明随机质量；
  • 每个逻辑样本拥有不重叠 sequence/counter；
  • 与 Black-Scholes 闭式解对照，误差应随1/N1/\sqrt{N}1/N​ 统计下降；
  • 报告置信区间而不是只报一个浮点值。

并行粒度

thread i:
  local_sum = 0
  repeat K samples:
      z = rng(sample_id)
      payoff = simulate(z)
      local_sum += payoff
  block_reduce(local_sum)

grid result → second-stage reduce / CUB

每线程多个样本能摊销 RNG state 和 launch 成本，但增加寄存器及串行工作。扫描 K 并看 occupancy、instruction throughput 和总时间。

用例三：稀疏图 BFS

目标：在 CSR 图上从源点计算无权最短层级。它展示 GPU 不擅长的负载不均、随机内存与动态 frontier。

CSR 与 Frontier

row_offsets[v]..row_offsets[v+1] → v 的邻边

frontier level L: [v2, v8, v9]
      │ expand neighbors
      ▼
candidate vertices
      │ visited atomic / duplicate removal / compact
      ▼
frontier level L+1

基线 Kernel

__global__ void expand(const int* frontier, int frontier_size,
                       const int* row, const int* col,
                       int* distance, int level,
                       int* next, int* next_size) {
    for (int i = blockIdx.x * blockDim.x + threadIdx.x;
         i < frontier_size;
         i += blockDim.x * gridDim.x) {
        int v = frontier[i];
        for (int e = row[v]; e < row[v + 1]; ++e) {
            int u = col[e];
            if (atomicCAS(&distance[u], -1, level + 1) == -1) {
                int pos = atomicAdd(next_size, 1);
                next[pos] = u;
            }
        }
    }
}

它正确直观，但高 degree vertex 由一个线程串行处理，next_size 又形成全局原子热点。

逐步优化

  1. Warp-centric：一个 warp 合作处理高 degree vertex；
  2. 分级调度：小 degree 每线程、中 degree 每 warp、大 degree 每 block；
  3. Block queue：先写 shared queue，再批量 reserve global slots；
  4. Prefix-sum compaction：用 scan 替代逐元素 global atomic；
  5. Direction optimization：frontier 很大时从 unvisited 顶点检查 incoming 邻居；
  6. Persistent/work stealing：degree 极不均时动态分配边范围。
degree distribution
small vertices ─→ thread lanes
medium vertices ─→ whole warp
large vertices ─→ whole block / split edge ranges

指标

BFS 的“有效工作”随图结构变化，不能只报 kernel 时间。至少报告：

  • traversed edges per second；
  • 每层 frontier size 与时间；
  • 重复 candidate 比例；
  • 原子次数与成功率；
  • global load efficiency、cache hit、warp divergence；
  • 与 CPU reference 的 distance 全量比较。

道路网、均匀随机图和幂律社交图表现完全不同，必须覆盖多种 degree 分布。

用例四：LLM Attention 推理片段

目标：解释 prefill 与 decode 下 attention 为什么需要不同 kernel，并把 GEMM、online softmax、KV cache 和多 GPU 串联起来。

O=softmax⁡(QKTd+M)VO=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}+M\right)VO=softmax(d​QKT​+M)V

朴素数据流

Q,K ─→ GEMM ─→ score[N,N] ─→ mask/softmax ─→ P[N,N]
                                                │
P,V ───────────────────────────────────────────→ GEMM → O

中间 score 与 P 的O(N2)O(N^2)O(N2) 显存流量是主要问题。FlashAttention 类算法按块计算 score，维护在线 softmax 统计量，不把完整矩阵写回 global memory。

Online Softmax 合并

对已经处理部分的最大值mmm、指数和lll 和输出累加ooo，加入新 tile 后：

m′=max⁡(m,mtile)m' = \max(m, m_{tile})m′=max(m,mtile​)

l′=em−m′l+emtile−m′ltilel' = e^{m-m'}l + e^{m_{tile}-m'}l_{tile}l′=em−m′l+emtile​−m′ltile​

o′=em−m′o+emtile−m′otileo' = e^{m-m'}o + e^{m_{tile}-m'}o_{tile}o′=em−m′o+emtile​−m′otile​

最终输出为o/lo/lo/l。这允许流式处理 K/V tiles，同时保持数值稳定。

Prefill 与 Decode

阶段形状特征常见瓶颈设计方向
Prefillquery 长，矩阵较大计算与 HBM 流量Tensor Core、tile、并行 sequence
Decode每步 query 很少，读取长 KV cachememory bandwidth、launch latency批处理、paged KV、融合、Graph

Decode 中 KV cache 的布局和分页元数据往往比单个矩阵指令更重要。

logical sequence pages
token 0..15  → physical page 7
token 16..31 → physical page 2
token 32..   → physical page 9

block table → gather K/V tiles → attention

工程组合

  • QKV projection 和 output projection 优先用 cuBLASLt/CUTLASS；
  • attention 核心可用优化框架、CUTLASS 或 Tile DSL，不从朴素 kernel 开始生产化；
  • RoPE、bias、mask、dequant 可在带宽允许时融合；
  • CUDA Graph 降低 decode 的重复 launch 开销；
  • KV pages 用 memory pool/VMM 管理时要区分逻辑容量和物理驻留；
  • tensor parallel 使用 NCCL collective，流水线并行还要处理 stage 间通信；
  • 量化必须同时定义权重、activation、scale、accumulator 和输出 dtype。

评估指标

不要只报某个 attention kernel 的 TFLOP/s：

  • time to first token；
  • inter-token latency；
  • tokens/s 与 batch/sequence 的关系；
  • KV cache bytes/token 和最大并发序列；
  • HBM bandwidth、Tensor Core utilization；
  • 数值误差、困惑度或任务质量；
  • 多 GPU scaling 与通信占比。

性能回归门禁

每个基准保存：

  • GPU UUID/型号、CC、功耗/时钟策略；
  • Driver、Toolkit、库、编译器与 git revision；
  • 输入 shape、dtype、分布和随机 seed；
  • 编译参数、算法 ID、workspace；
  • warmup、repeat、统计量；
  • kernel time、端到端 time、bytes/FLOPs 和误差。

门禁用区间而非单次值。例如以稳定机器的 median 与 P95 比较，只有超过噪声阈值才失败。共享开发机上的自动频率和其他进程会制造假回归。

CUDA 术语速查

术语含义不要混淆
ThreadSIMT 中最小逻辑执行实例不是独立 CPU core
Warp32 个线程的调度组分支后仍是同一 warp 的 active masks
Block/CTA可共享 shared memory 并 block-sync 的线程组默认不能与其他 block 同步
Grid一次 kernel launch 的 blocks 集合与 cooperative grid 保证不同
SM执行 warp 的多处理器CUDA Core 只是其一种单元
GPC包含多个 SM 等资源的更高硬件分组Cluster 通常在此范围协同
Occupancyactive warps 相对上限的比例不是利用率或性能本身
Coalescingwarp 访问合并为高效内存事务不等于 cache hit
Shared memoryblock 作用域片上软件管理存储与 L1 可能共享物理资源但语义不同
Local memory每线程地址空间，常落在 device memory名字不表示片上
UVA统一虚拟地址空间不等于页面自动迁移
Unified Memory可迁移/统一管理的内存机制不等于始终零拷贝
Pinned memory不可分页 host memory过量会伤害系统
Stream有序工作队列不保证不同 stream 必然并发
Eventstream 时间点/依赖对象timing event 与同步需求要区分
PTX虚拟 GPU ISA不是最终硬件指令
SASS特定 GPU 机器指令不具备跨架构可移植性
Tensor Core矩阵/张量运算单元不是所有 shape/dtype 自动使用
TMAdescriptor 驱动的 tensor 搬运单元不执行矩阵乘法
DSMcluster 内分布式 shared memory不是全 GPU 通用 shared memory
Tile多维值/工作分区抽象不等于固定一个 warp
Memory poolallocation backing 的缓存与复用策略reserved 不等于 used
VMM虚拟地址与物理 allocation 显式映射不自动提供同步

毕业检查表

学完后，应能对一个 CUDA 项目给出以下可验证答案：

  1. 工作如何映射到 grid/block/warp 或 tile program？
  2. 每个输出元素需要搬运多少字节、做多少运算？
  3. 哪些数据在 register/shared/L2/HBM/host/fabric 中流动？
  4. 所有跨线程、stream、device、进程依赖如何建立 happens-before？
  5. 数值误差预算与 reference 是什么？
  6. 为什么选择库、SIMT、Tile 或多 GPU？
  7. profiler 证据指向哪个瓶颈？
  8. 优化对端到端时间而非单 kernel 有何影响？
  9. 不支持某项能力的 GPU 走哪条 fallback？
  10. 构建、测试、部署与性能结果能否在另一台机器复现？
