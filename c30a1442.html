UAbilityTask

Unreal Engine, GamePlay, Game Ability System 2025-08-10 2026-10-10 2001 字

自动关联目录：UAbilityTask

AbilityTask 是技能里的"异步步骤"。它存在的理由很直接：技能逻辑里经常要"等一下"（等动画放完、等玩家按键、等目标命中），而直接挂委托或用定时器会脱离 GAS 的管理——技能被取消时它们不会跟着停。

一句话定位：判据只有一条——这段等待应该在技能被打断时一起停止吗？是，就必须是 Task。

1. 为什么不用定时器

做法问题
GetWorld()->GetTimerManager().SetTimer不随技能取消；不参与预测；无法回滚
直接绑动画委托同上，且容易重复绑定
Latent 蓝图节点只能在蓝图里用
UAbilityTask生命周期由 Ability 管理，取消即结束

这条判据是硬性的一——用定时器做技能等待，在单人测试里完全正常，一旦加入"被打断"就会漏（眩晕时技能停了但伤害照出）。

2. 内置常用 Task

Task用途
UAbilityTask_PlayMontageAndWait播放蒙太奇并等待结束/取消/事件
UAbilityTask_WaitGameplayEvent等待一个 Gameplay Event（动画通知触发）
UAbilityTask_WaitGameplayTag等待标签的添加/移除
UAbilityTask_WaitAttributeChange等待某属性变化到阈值
UAbilityTask_WaitInputPress/Release等待输入（蓄力）
UAbilityTask_WaitDelay等待一段时间
UAbilityTask_WaitTargetData等待目标选择（配合 TargetActor）
UAbilityTask_WaitConfirmCancel等待确认/取消
UAbilityTask_NetworkSyncPoint等待两端同步点
UAbilityTask_ApplyRootMotion*根运动位移

3. 用法

auto* Task = UAbilityTask_PlayMontageAndWait::CreatePlayMontageAndWaitProxy(
    this, NAME_None, MontageToPlay);
Task->OnCompleted.AddDynamic(this, &ThisClass::OnCompleted);
Task->OnBlendOut .AddDynamic(this, &ThisClass::OnCompleted);
Task->OnInterrupted.AddDynamic(this, &ThisClass::OnCancelled);
Task->OnCancelled.AddDynamic(this, &ThisClass::OnCancelled);
Task->ReadyForActivation();   // 必须调用
要点说明
ReadyForActivation()不调用 Task 不会启动——最常见的"技能卡住"原因
四个回调都要处理只处理 OnCompleted 会导致被打断时技能永远不结束
Task 随 Ability 结束自动清理但仍要在 OnDestroy 里解绑外部委托

蒙太奇 Task 的四个回调语义不同，必须区分：

回调时机
OnCompleted正常播完
OnBlendOut开始混出（通常等同完成）
OnInterrupted被别的蒙太奇打断
OnCancelled被取消（技能被打断）

4. 自定义 Task

当内置 Task 不够时（比如等待一次自定义的网络回包）：

要实现的说明
Activate()启动逻辑
OnDestroy(bool bInOwnerFinished)清理（Ability 结束时会调用）
静态工厂 CreateXxxProxy创建并设置 InitTask(*Ability)
输出委托 UPROPERTY(BlueprintAssignable)供蓝图绑定
bTickingTask / bSimulatedTask是否需要 Tick / 是否在模拟端运行
UCLASS()
class UAbilityTask_WaitMyThing : public UAbilityTask
{
    GENERATED_BODY()
public:
    UPROPERTY(BlueprintAssignable)
    FMyTaskDelegate OnFinished;

    static UAbilityTask_WaitMyThing* CreateTask(UGameplayAbility* OwningAbility);

    virtual void Activate() override;
    virtual void OnDestroy(bool bInOwnerFinished) override;
};

要点：资源必须在 OnDestroy 里释放，因为技能随时可能因为被眩晕而取消。

5. 代价与权衡

设计收益代价什么时候不该用
Task 等待随技能取消、参与预测比定时器多几行代码与技能无关的全局等待不必用
bSimulatedTask模拟端也跑同步表现增加复杂度只需 Ownership 端的逻辑不要开
bTickingTask能每帧推进有 Tick 开销能用事件驱动就不要开
WaitDelay最简单只是到点执行，要确保取消路径也处理长流程不该靠它串
自定义 Task任意等待语义要正确处理生命周期内置能覆盖就用内置

6. 踩坑与排查

坑现象怎么验证
忘了 ReadyForActivation()Task 不运行，技能卡住检查每个 Task 后是否调用
只绑 OnCompleted被打断后技能永远不结束四个回调都要接
在 Task 里直接改属性不走 GE，预测与复制出问题应 Apply GE
用 WaitDelay 做长流程到时间就执行，不随打断停止检查取消路径
自定义 Task 没在 OnDestroy 解绑回调到已销毁对象OnDestroy 里清理
Task 里持有裸指针对象已销毁用 TWeakObjectPtr
模拟端表现不同步没设 bSimulatedTask确认该 Task 是否需要在模拟端跑
蒙太奇打断后技能不结束没接 OnInterrupted补回调
嵌套多个 Task状态机失控复杂流程应拆分或引入状态

7. 排查顺序

1. 技能卡住？→ 先看有没有 ReadyForActivation()
2. 打断后不结束？→ 四个回调是否都接了
3. 表现不同步？→ bSimulatedTask
4. 崩溃？→ OnDestroy 是否解绑、有没有裸指针
5. 数值变化异常？→ Task 里是否直接改了属性而非 Apply GE
