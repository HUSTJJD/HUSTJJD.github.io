2 Application Layer

Base Knowledge, Computer Network 2025-08-10 2026-10-11 4216 字

应用层在做什么

应用层是唯一"用户看得见"的层。它的全部工作就是：定义通信双方交换的消息格式和交互顺序。

与下层不同，应用层协议没有通用框架——每个协议自己定义自己的语义。但有几样东西是共通的：

  • 进程如何标识（IP + 端口）
  • 数据如何交换（socket API）
  • 消息如何表示（文本 or 二进制）

应用架构

架构特点例子
C/S（客户-服务器）服务器常开、有固定 IP；客户端间歇连接Web、邮件、FTP
P2P（对等）无中心服务器，每个节点既是客户又是服务BitTorrent、早期 Skype
混合中心节点做索引/协调，实际数据 P2P 传输BitTorrent 的 tracker、现代视频会议

C/S 的扩展问题：一台服务器扛不住时，用数据中心 + 负载均衡。

P2P 的扩展优势： peers 越多，总带宽也越多（BitTorrent 的"下载的人越多越快"）。代价是管理困难（节点随时上下线）、激励问题（搭便车者）。

Socket：应用与网络的接口

Socket 是应用层和传输层之间的门。应用程序通过它选择传输层协议（TCP/UDP）并收发数据。

   应用进程
      │  socket API（send/recv）
      ▼
   Socket（由 OS 管理）
      │
      ▼
传输层 → 网络层 → 链路层

关键认知：socket 不是协议，是 API。它把"用哪个传输层协议"这个选择暴露给应用：

int s = socket(AF_INET, SOCK_STREAM, 0);   // TCP
int u = socket(AF_INET, SOCK_DGRAM,  0);   // UDP

TCP socket 编程模型：

服务器:                          客户端:
  socket()                         socket()
  bind(监听地址:端口)              connect(服务器地址)
  listen()                          send()/recv()
  accept()  ← 阻塞等连接            close()
  recv()/send()
  close()

accept() 返回的是新 socket——监听 socket 只负责接受连接，实际通信用新 socket。所以服务器能同时维持成千上万连接。

DNS

DNS（Domain Name System）是互联网的电话簿：把人类可读的域名映射成 IP 地址。

为什么需要 DNS

  • 人记不住 IP
  • IP 会变（换机房、迁移到云），域名不变
  • 负载均衡：一个域名对应多个 IP，每次返回不同的（简单的 round-robin）

层次结构

                   根服务器（13 组，.）
                        │
    ┌───────────┬───────┴────┬───────────┐
   com         edu          org         cn
    │                                    │
example.com                          edu.cn
    │                                    │
www.example.com                    hust.edu.cn

完整的域名从右往左读，最右是根（通常省略结尾的点）。www.example.com. 才是完全限定域名（FQDN）。

三类服务器：

  • 根域名服务器：13 组（A~M），实际上有上千台镜像（任播）
  • 顶级域（TLD）服务器：.com、.cn、.edu
  • 权威域名服务器：真正持有某域名记录的服务器

查询方式

  • 递归查询：我替你查到底，你把最终结果给我（客户端 → 本地 DNS 服务器）
  • 迭代查询：我不知道，但我告诉你下一家去问谁（本地 DNS 服务器 → 根/TLD/权威）
客户端 → 本地DNS:  www.example.com 的 IP？（递归）
本地DNS → 根:      谁知道 .com？      （迭代）
根     → 本地DNS:  去问 a.gtld-servers.net
本地DNS → TLD:     谁知道 example.com？（迭代）
TLD    → 本地DNS:  去问 ns1.example.com
本地DNS → 权威:    www.example.com 的 IP？（迭代）
权威   → 本地DNS:  93.184.216.34
本地DNS → 客户端:  93.184.216.34

记录类型

类型含义示例
A域名 → IPv4example.com. 3600 IN A 93.184.216.34
AAAA域名 → IPv6example.com. IN AAAA 2606:2800::...
CNAME别名 → 规范名www.example.com. IN CNAME example.com.
NS域名 → 该域的权威服务器example.com. IN NS ns1.example.com.
MX邮件交换example.com. IN MX 10 mail.example.com.
TXT任意文本SPF、域名验证
SOA权威区域的起始记录主服务器、序列号、刷新间隔
PTR反向解析（IP → 域名）34.216.184.93.in-addr.arpa.

缓存

DNS 到处都在缓存：浏览器 → OS → 本地 DNS 服务器 → 各级。缓存靠 TTL 控制有效期。

这也是为什么改 DNS 记录后要等一段时间才生效——各地缓存的 TTL 还没过。

# 查看各级缓存
ipconfig /displaydns          # Windows 本地缓存
sudo killall -INFO mDNSResponder  # macOS 刷新
systemd-resolve --statistics  # Linux systemd-resolved

DNS 的问题

  • 安全性：原始 DNS 是明文 UDP，可被劫持/污染。解法是 DNSSEC（签名，防篡改）和 DoH/DoT（DNS over HTTPS/TLS，防窃听）
  • 性能：每次访问前都要一次额外往返。解法是缓存 + 预解析（浏览器提前解析页面里的域名）
  • CNAME 链：CNAME 指 CNAME 再指 A，会拖慢解析。尽量控制在 1~2 层

HTTP

HTTP（HyperText Transfer Protocol）是 Web 的基石。请求-响应模型，客户端发起、服务器应答。

报文格式

请求：

GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html
Connection: keep-alive
                              ← 空行
[请求体]

响应：

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Cache-Control: max-age=3600
                              ← 空行
<!DOCTYPE html>...

空行分隔头部和实体——这是 HTTP 报文格式最关键的一条规则。

方法

方法语义幂等安全
GET获取资源✓✓
HEAD只要响应头✓✓
POST提交数据（语义由应用定义）✗✗
PUT整体替换资源✓✗
PATCH部分修改✗✗
DELETE删除✓✗
OPTIONS查询支持的方法 / CORS 预检✓✓

幂等（多次执行效果相同）和安全（不修改服务器状态）是设计 API 时真正要关心的性质。GET 应该是安全的——不要写"GET /delete?id=1"。

状态码

类别含义常见
1xx信息100 Continue、101 Switching Protocols（WebSocket）
2xx成功200 OK、201 Created、204 No Content、206 Partial Content
3xx重定向301 永久、302 临时、304 Not Modified（缓存命中）、307/308 保持方法
4xx客户端错400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、429 Too Many Requests
5xx服务端错500 Internal、502 Bad Gateway、503 Unavailable、504 Gateway Timeout

301 vs 302：301 会被浏览器永久缓存（之后直接跳，不再问服务器），302 每次都问。改错了要清浏览器缓存才能恢复，这是个著名的坑。

401 vs 403：401 是"你没认证"（没带/带错凭据），403 是"认证了但没权限"。

连接的演进

HTTP/1.0：每个请求一个 TCP 连接。三次握手 + 慢启动，开销巨大。

HTTP/1.1：

  • 持久连接（keep-alive）：一个连接上发多个请求
  • 流水线（pipelining）：不等响应就连发多个请求。但**队头阻塞（HOL blocking）**问题严重，实际浏览器几乎都不开

HTTP/2：

  • 二进制分帧：不再是纯文本
  • 多路复用：一个连接上并行多个流，解决 HTTP 层队头阻塞
  • 头部压缩（HPACK）
  • 服务器推送（实践中效果不佳，已基本弃用）

但 HTTP/2 的多路复用仍然跑在 TCP 上，TCP 层的队头阻塞还在——一个包丢了，所有流都要等重传。

HTTP/3：跑在 QUIC（UDP 之上）上，彻底解决队头阻塞，连接建立也更快（见传输层章节）。

Cookie 与 Session

HTTP 本身无状态。要维持登录态就要外挂机制：

  • Cookie：服务器通过 Set-Cookie 下发，浏览器后续自动带上 Cookie
  • Session：服务器端存状态，Cookie 里只放一个 session id

Cookie 属性：

Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600; Path=/
属性作用
HttpOnlyJS 读不到（document.cookie 拿不到），防 XSS 窃取
Secure只在 HTTPS 下发送
SameSite限制跨站发送，防 CSRF。Strict/Lax/None
Max-Age/Expires有效期
Domain/Path作用范围

缓存

缓存是 Web 性能的第一杠杆。

强缓存（不发请求）：

Cache-Control: max-age=31536000        # 一年内直接用本地
Cache-Control: no-cache                # 每次都要协商
Cache-Control: no-store                # 不许存
Cache-Control: private / public        # 能否被共享缓存存

协商缓存（发请求问"变了吗"，没变就 304）：

# 首次响应
ETag: "abc123"
Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT

# 后续请求
If-None-Match: "abc123"
If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT

# 未变 → 304 Not Modified（无响应体）

实践套路：带内容哈希的文件名（app.a1b2c3.js）配 max-age=31536000, immutable；HTML 用 no-cache。这样既能永久缓存静态资源，又能通过改 HTML 里的文件名立即更新。

HTTPS / TLS

HTTPS = HTTP + TLS。TLS 提供三件事：

  1. 机密性：加密，窃听者看不到
  2. 完整性：MAC，篡改能被发现
  3. 身份认证：证书证明"你连的确实是 example.com"

TLS 1.3 握手（1-RTT，会话复用时 0-RTT）：

Client                                    Server
  │──── ClientHello (支持的套件, key_share) ──►│
  │◄─── ServerHello, key_share, ─────────────│
  │     {EncryptedExtensions}, {Certificate},
  │     {CertificateVerify}, {Finished}      │
  │──── {Finished} ─────────────────────────►│
  │══════ 应用数据 ══════════════════════════│

TLS 1.2 要 2-RTT，1.3 降到了 1-RTT。别小看这一个 RTT——跨太平洋 100 ms，每个新连接省 100 ms 是实打实的体验提升。

证书链验证：浏览器内置根 CA → 中间 CA → 站点证书，逐级验签。自签证书之所以被浏览器警告，就是因为它不在信任链里。

常见坑

  • Host 头不是可有可无：HTTP/1.1 靠它做虚拟主机（一台服务器多个域名）。缺了会 400
  • GET 带 body：规范没禁止，但很多代理/服务器会忽略。别这么干
  • Connection: keep-alive 在 HTTP/2 里是非法头：HTTP/2 有自己的连接管理
  • Cookie 没设 SameSite：现代浏览器默认 Lax，跨站场景会突然失效
  • 证书过期：自动化运维里最常见的故障。用 Let's Encrypt + 自动续期
  • DNS 缓存导致灰度不生效：改了 DNS 但用户还连老 IP。灰度要靠应用层路由，别依赖 DNS
  • 把 HTTPS 当成"绝对安全"：TLS 只保护传输过程，两端（客户端和服务器）上的数据仍是明文
